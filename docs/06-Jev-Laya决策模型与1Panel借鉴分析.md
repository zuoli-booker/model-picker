## 一、Jev 与 Laya 是什么

两者同属 2026 年 9 月爆火的新品类：**"System 1" 非自回归决策模型**——不做文本生成，输入一段文本（state）+ 一组预定义的类型化问题（choice 选择题 / score 打分 / noul 是非概率），一次前向传播直接输出每题的概率分布和置信度。**零输出 token、毫秒级延迟、不会幻觉**。

| | **Jev** | **Laya** |
|---|---|---|
| 出品 | TypeSafe AI（前 OpenAI 研究员 Diogo Almeida，$40M 种子轮，DCVC 领投） | Nandakishor M / Convai Innovations（印度独立开发者） |
| 发布时间 | 2026-09-15 | 2026-09-18（Jev 发布后 3 天） |
| 形态 | 闭源托管 API（typesafe.ai，亦上 OpenRouter/Vercel/Cloudflare） | **开源：Apache-2.0，代码+权重全开放** |
| 参数量 | 未公开 | 421M（英文 ModernBERT）/ 322M（多语言 mmBERT，100+ 语言含中文） |
| 价格 | $0.042/MTok 输入，输出免费 | 免费（自托管，CPU 可跑） |
| 速度 | ~236-523ms（含网络） | T4 GPU 33ms / CPU 200-460ms / 批处理 7.2ms |
| 选项上限 | Choice 最多 255 项 | 约 20 项后准确率明显下降 |
| 生态热度 | 内测 36 小时清 14 万人 waitlist | **9 天 2.3万-2.7万★**，Hugging Face 趋势第一，HF CEO 亲自背书 |
| 关键短板 | 厂商自测数据为主，不可自托管，数据出境 | **零样本接近随机**（typed-decisions 基准 0.36 vs 随机 0.318），需微调才可用；多选项场景大幅落后 Jev；置信度校准偏高 |

**一句话**：Jev 是"托管版决策模型"，Laya 是"开源版决策模型"。品类本身已被验证（9 天 2.7 万★说明痛点真实：LLM-as-a-judge / 路由决策太贵太慢），但 Laya 开箱即用性被作者自己标注为"Honest limits"——**必须微调**。

## 二、对 router 项目的价值：你的直觉是对的，但有明确的适用边界

### 2.1 我们的路由决策现状

当前 MVP 的决策链：**用户在 CLI 里人工选任务类型** → 规则引擎按任务-维度权重表选模型。决策是"静态、人工触发"的。

### 2.2 决策模型能补哪一环

路由应用（L4，Docker BYOK）上线后，真实场景是：**用户的智能体发进来一段请求，没人替它选任务类型**。这是规则式路由做不到的——除非让用户写规则，那就回到 Martian 失败的老路。决策模型恰好补这个洞：

```
智能体请求 → [Laya 本地 sidecar] 任务分类（choice：6种任务类型）+ 质量敏感度（noul）
           → 置信度 ≥ 阈值：自动路由到策略对应模型
           → 置信度 < 阈值：回退规则引擎 / 按首选模型执行
           全程 30-460ms、零 API 费用、数据不出本机
```

这正好同时满足我们三条硬约束：**不重复造轮子**（直接调 Laya，Apache-2.0）、**BYOK 数据不出境**（Laya 跑在用户自己容器里，Jev 托管版反而不符合这条）、**可解释**（输出的是概率分布，可记录每次决策的理由）。

### 2.3 但必须泼两盆冷水

1. **Laya 零样本不可用**（作者自己承认）。任务分类要可用，需要在标注数据上微调（官方提供 Kaggle 免费 GPU 4-5 小时的微调 notebook）。这意味着我们要维护：标注数据集 + 微调管道 + 阈值校准——**这是一条持续的维护线**，不是一次性集成。
2. **选项多了就不行**（>20 选项准确率骤降）。我们的场景是"6 种任务类型"（choice 选项少 ✅）和"从用户 3-8 个模型里选一个"（选项少 ✅）——场景恰好落在 Laya 的舒适区，这是好消息。

### 2.4 结论与建议（待确认）

| 项 | 建议 |
|---|---|
| 时机 | **不进入 MVP / 阶段1**。列为阶段3（产品化闭环之后）的"智能决策模式"增强项 |
| 选型 | 只用 **Laya**（Apache-2.0 + 本地跑，符合 BYOK；Jev 托管版数据出境，违背项目立身之本，仅作对标参考） |
| 形态 | 路由应用内嵌 **Laya sidecar 容器**（laya-serve 已提供 Jev 兼容的 HTTP 接口），默认关闭，配置里一键开启 |
| 决策闸 | 过 AGENTS.md 第 7 条：先验证微调后在我们的 6 任务分类上准确率 ≥85% 再集成；微维护成本预估 >2h/月则降级为"实验性插件" |
| 数据冷启动 | 微调数据集可以来自 MVP 的用户选择日志（用户选的任务类型 = 天然标注），这是我们自己独有的数据资产 |

**给左力的一句话**：这是一个"方向正确、时点未到"的增强——先把规则式路由跑起来积累选择日志，日志就是未来微调 Laya 的燃料，届时集成是顺水推舟。

## 五、补充调研（2026-09-29 上午）：1Panel 的 Jev/Laya 具体实现 & 我们的衔接方案

> 触发：左力提出"让用户自己添加 Jev 模型来做智能切换"，并要求深挖 1Panel 的 Jev/Laya 模块。

### 5.1 我方原方案的路由切换机制（现状核实，来自 yaml_gen.py 代码）

**当前 MVP 的"切换"发生在配置生成时，不是运行时**：

```
用户跑 CLI 问答 → 规则引擎算出每任务首选/备选 → 生成 LiteLLM config（静态）
运行时：应用调任务别名（writing/coding/...）→ LiteLLM 映射到首选模型
        首选失败 → fallback 到 <task>_backup 备选
```

- **任务级切换**：应用侧主动换别名（写作用 writing、编码用 coding）
- **失败级切换**：LiteLLM fallback（仅在首选模型故障时触发）
- **缺失的一环**：**请求级动态判断**——应用发一段请求进来，没人替它判断该走哪个任务别名。这正是 Jev/Laya 能补的位置，也是"智能切换"的确切含义。

### 5.2 1Panel AI 网关 v1.3 的 Jev 模式（2026-09-28 发布，与我们设想同构）

架构：**统一 auto 入口 → Jev 决策 → 网关调度**。

| 机制 | 1Panel 的做法 | 对我们的借鉴价值 |
|---|---|---|
| **auto 入口** | 业务应用统一用 `auto` 作模型名，不感知路由逻辑 | ⭐⭐⭐ 路由应用加一个 `auto` 别名，智能体只管发请求 |
| **路由目标定义** | 管理员定义 2-10 个目标：名称 + 适用说明 + 排除说明 + 示例 + 关联模型组，**全自然语言，无需样本** | ⭐⭐⭐ **与 model-picker 完美衔接**：我们的 6 任务类型定义（含维度权重说明）可直接生成目标定义文件 |
| **两种模式并存** | 向量模式（简单/复杂二分，需样本校准）与 Jev 模式（多目标语义）可切换，配置互保留 | 对应我们"规则式（默认）+ 智能式（可选）"双模式，规则式永远兜底 |
| **兜底 + 熔断** | Jev 返回 other/超时/限流/不可用 → 进兜底模型组；连续异常熔断，防止决策服务故障放大 | 必抄：决策引擎挂了路由应用照常工作（回退规则式首选模型） |
| **数据边界** | 只向 TypeSafe 发**截断后的当前用户文本** + 2 个必要特征（是否含工具声明/是否截断），不发历史消息、凭据、模型组信息 | 必抄：这是 Jev 模式（数据出境）能过合规的关键设计，写进我们的实现规范 |
| **决策日志** | 记录目标、概率、置信度、Token、时延、回退原因；"测试路由"对话框可视化 | 抄：可解释性 UI，和我们"每条推荐有理由"的产品理念一致 |

### 5.3 1Panel 应用商店的 Laya Server（9-24 上架）

**"Jev 开源替代：自托管的 Laya 决策引擎 API 与控制台"**——一键安装、CPU 可跑、内置多语言模型（含中文）、Web 控制台 + API Key 管理、**接口完全兼容 Jev 线协议**（`POST /v1/systemone`，客户端只需换 baseUrl）。

**这给我们的关键启示：Jev 和 Laya 是可互换的双引擎**——我们的路由应用可以让用户二选一：
- **Jev 模式**：用户自己填 TypeSafe API Key（BYOK，$0.042/MTok，无本地资源需求）
- **Laya 模式**：Docker 包内嵌 laya-serve sidecar（免费、数据不出机，但需承担 CPU/内存，且需微调后才可用）

### 5.4 左力设想的技术确认：用户自添加 Jev 做智能切换——**架构上成立**

1. **合规成立**：用户填自己的 TypeSafe Key = BYOK，数据出境是用户自己的选择，我们只提供选项并在文档中明示边界（照抄 1Panel 的"只发截断文本+最小特征"设计）
2. **架构成立**：Jev 不进我们的模型清单（它不生成文本，不是被路由的对象），而是作为**决策引擎**配置项——和用户的手头模型清单正交
3. **衔接成立**：model-picker 未来新增第 4 种产物——`routing-goals.yaml`（从 6 任务定义自动生成的 Jev/Laya 目标定义：名称+适用+排除+示例），用户导入路由应用即启用智能模式
4. **时点判断（维持）**：这属于 L4 路由应用（阶段2 产物）的能力。但有个可以提前的低成本动作——**MVP 的 quiz.py 里记录用户任务选择日志**（本地、匿名、用户可选上传），为未来微调 Laya 或校准目标定义积累标注数据

### 5.5 修订后的智能路由架构图（L4 目标形态）

```
智能体/应用 ──(model=auto)──▶ 路由应用（Docker，用户自托管）
                                │
                                ├─ 决策引擎（二选一，用户配置）
                                │   ├─ Jev API（用户自己的 TypeSafe Key，BYOK）
                                │   └─ Laya sidecar（本地免费，数据不出机）
                                │      ↓ Choice: 属于哪个任务目标（2-10 个）
                                ├─ 概率+置信度 → 置信度≥阈值：进对应任务别名
                                │              → <阈值/超时/熔断：进兜底别名（规则式首选）
                                │
                                └─ LiteLLM 调度（model-picker 生成的任务别名+fallback）
                                      ↓
                                用户自己的各模型 Key（BYOK，请求不经我们）
```
