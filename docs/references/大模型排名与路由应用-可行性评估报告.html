大模型性能排名网站 + 大模型路由应用 · 可行性评估报告

产品定位（经用户修订确认）：① 纯聚合各主流榜单最新排名的模型性能网站（不自建评测）；② 用户自带 API Key / URL / 模型名（BYOK）的策略生成器 + 可下载自托管路由应用，按速度 / 质量 / 成本偏好生成路由策略，智能体经 OpenAI 兼容 API 调用。

调研日期：2026-09-28 ｜ 版本：修订版（纳入"纯聚合 + BYOK 无托管"定位）
本版相对初稿的关键修订：① 排名站不做任何自测，仅做榜单聚合与导航——砍掉全部实测成本；② 路由应用为 BYOK 自托管模式，平台不经手任何 API Key 与模型调用——基本消除"代调 API / 数据出境 / 生成式 AI 备案"等合规风险；③ 策略为"榜单数据 + 用户偏好"的规则式生成，不做学习式语义路由，整体难度与成本显著下调。

结论速览（TL;DR）

  • 两个赛道都有成熟玩家，但你的组合仍有空白：排名侧有 LMArena、Artificial Analysis、DataLearner；路由侧有 OpenRouter、LiteLLM、One-API。"榜单聚合 → 按自己可用模型生成策略 → 下载自托管路由"这条闭环目前无直接竞品。
  • "不自测 + BYOK"是正确且聪明的减法：砍掉最贵的数据实测成本和最重的合规风险，产品变成纯"信息聚合 + 配置工具"，一个人即可长期运营。
  • 不重复造轮子：榜单数据靠官方 API 与公开数据聚合；路由底座直接用 LiteLLM（55k★，MIT）；自研只有"策略配置器 + 榜单数据管道"两块。
  • 方案可行性高，建议两期走：P0 排名聚合站（约 3-5 周，难度低）→ P1 策略配置器 + 可下载路由（约 5-7 周，难度中）。学习式路由降级为远期可选。
  • 最难的是长期数据维护：榜单口径对齐、模型命名归一化、更新自动化——80% 的工作量在这里，不在开发。
  • 成本极低：个人模式首年现金投入约 ¥1,500-5,000（服务器+域名），无实测 API 费用；主要成本是 1 人 × 2-3 个月业余时间。
  • 法律风险基本可控：BYOK 自托管 = 工具软件模式，平台不接触 Key、不经手请求；剩余风险点是榜单数据引用授权与开源协议（避开 AGPL 的 New API）。
  • 用户价值真实但强度分层：排名站是流量入口（弱-中价值），策略生成是差异化决策价值（中），路由应用是日常留存价值（中-强）；最大隐忧是"选模型"为低频决策，需靠"模型换代提醒 + 用量看板"设计持续回访理由。

2.4 核心隐忧：低频 + 一次性 = 用户来了就走

这是方案在用户侧最大的结构性风险："选模型、配策略"是低频行为。用户配好一次路由后，没有理由再回网站——直到他忘了你。没有回访就没有传播、没有口碑积累、没有数据飞轮。必须在产品设计里人为创造持续价值：

机制做法创造的回访理由
模型换代提醒用户保存自己的模型清单与策略；当榜单出现"比你当前选择更强/更便宜"的新模型时，邮件/微信/站内推送"你的策略该更新了"最强留存钩子 把低频决策变成持续订阅服务
用量与成本看板路由应用本地统计各模型调用量/成本/延迟，同步到网站可视化（可选、匿名）高频查看入口，让路由"可感知"
策略版本管理策略可保存多版本、对比效果、一键回滚把"调策略"变成持续优化动作
榜单周报/月报"本月榜单变化摘要"内容化推送，SEO + 订阅双引擎内容型留存，服务流量基本盘

其中"模型换代提醒"是必做项——它恰好复用 P0 的数据管道（你本来就在追榜单变化），边际成本极低，却把产品从"一次性工具"升级为"订阅式选型顾问"。

2.5 会不会有人用：最终判断

  • "来"的理由成立：痛点真实（有 LiteLLM/OpenRouter 的 Star 数与调用量佐证）、组合无直接竞品、"帮我基于手头模型配好能跑的路由"这句话目标用户一听就懂。获客主通道是排名站 SEO（"XX模型排名/对比"类搜索词量大且精准）+ 路由应用挂 GitHub 开源引流。
  • "用"的理由成立但有条件：用户价值公式 = 节省的调研时间 + 避免选错模型的成本 + 换模型不改代码的工程便利 > 学习成本（登记 Key、理解策略、部署 Docker）。前两者成立，所以必须把学习成本压到最低——一键 Docker、策略解释可视化、默认推荐"开箱即用"。
  • "留"的理由需要设计：不做"换代提醒 + 用量看板"，产品就是一个用完即走的工具；做了，就是持续服务的选型顾问。这两个功能应从 P1 就纳入，不要拖到远期。
  • 商业化预期要现实：个人开发者付费意愿低（开源免费是底色），小团队/企业才是付费方（私有化部署支持、团队版策略协作、优先数据更新）。建议定位"开源工具 + 数据服务"，而非 SaaS 收费工具。

  • 成本：1 人 5-7 周；无 API 费用。

三大最难环节（修订后重新排序）

  1. 数据新鲜度与口径维护（长期最难，不可替代）：榜单每周变、模型每月换代、同一模型在不同榜单名字不同。产品价值 = 数据可信度 × 更新速度。P0 就要把管道做成全自动 + 更新失败告警 + 每分数标注来源与时间。
  2. "任务类型 → 榜单维度 → 加权推荐"的规则设计（产品壁垒所在）：凭什么推荐这个模型？映射规则要基于公开榜单可解释地推导，并向用户展示推理过程。不靠自测，靠对榜单方法的深入理解——是认知壁垒而非资金壁垒。
  3. 数据引用授权与开源协议（低成本但必须做对）：①优先用官方 API，页面标注来源并回链；②底座只用 MIT/Apache-2.0（LiteLLM / One-API / AISIX），避开 AGPL 的 New API；③榜单页面转载条款逐个确认。

五、法律与合规边界（BYOK 模式专项分析）

✅ BYOK + 自托管 + 纯聚合的组合，把原方案最大的三类合规风险基本消除：
  • 不涉及 API 转售/代调：Key 由用户填入自己部署的路由应用，请求不经过你的服务器——你不是"API 中转站"，不适用相关监管口径。
  • 不涉及生成式 AI 服务备案：你不向公众提供生成内容，只是工具软件 + 信息聚合。
  • 不涉及数据出境与隐私问题：用户 prompt 全在用户自己的基础设施内流转。

仍需注意的四个点

  1. 榜单数据引用授权：优先官方 API + 标注来源 + 回链；对有明确转载限制的榜单（部分商业榜单），只做"跳转导航 + 摘要引用"，不整表搬运。
  2. 开源协议：LiteLLM（MIT）/ One-API（MIT）可嵌入分发；New API（AGPL）不可嵌入，只能让用户自行选用。
  3. 免责声明：排名数据来自第三方、推荐策略仅供参考，网站需有清晰的免责与数据来源声明。
  4. "跟我无法律关系"的边界：用户自带 Key 确实大幅切割责任，但你的策略推荐若明显错误（如推荐了已下线模型）仍属服务质量问题——靠数据更新机制和免责声明确保，而非法律架构。

六、关键风险提示

🦈

OpenRouter 与聚合榜站的上下夹击

OpenRouter 已覆盖"排名 + 统一调用 + 简单路由"；DataLearner 已覆盖"中文聚合榜单"。对策：死守两家都不做的空白——"基于用户手头模型集合的透明策略生成 + 可下载自托管路由"，并把榜单导航体验做到极致。

📉

不要把"省钱"当卖点

模型价格持续暴跌（GPT-4 级 16 个月降约 200 倍），语义路由赛道已整体降温。规则式策略天然规避了这个坑，但文案上同样应主打"选对模型、质量保障、一眼看懂"，而非"省 token 钱"。

🔄

榜单可信度危机波及

各榜单方法不同、冠军不同，简单拼表会被质疑专业性。对策：明确标注每个分数的来源、方法与更新时间，提供"按场景选榜"导航——把"帮用户选对榜单"做成特色。

🧊

工具型产品的冷启动

排名站是流量入口，路由应用是留存工具，但两者都需要冷启动流量。对策：排名站 SEO（"XX 模型 排名"类搜索词量大）+ 开源路由应用挂 GitHub 引流，形成"搜索进来看榜 → 顺便配策略 → 下载路由"的漏斗。

七、最终结论与行动建议（修订版）

  1. 方向可行，且"纯聚合 + BYOK"的修订定位是更聪明的版本：砍掉实测成本与合规风险，一个人即可开发和长期运营。
  2. 核心壁垒是认知与运营，不是代码：榜单方法理解（任务→维度映射规则）+ 数据管道的长期新鲜度维护。
  3. 技术栈全部站在开源肩膀上：排名站 fork 可视化项目 + 聚合官方 API；路由应用 = 自研策略层 + LiteLLM（MIT）打 Docker 包。不写网关、不测模型。
  4. 严格执行 P0 → P1 最小闭环：3-5 周做出排名站验证流量，5-7 周做策略配置器 + 可下载路由这个核心差异点。学习式路由只做远期可选。
  5. 现金门槛极低：首年约 ¥1,500-5,000；真正的投入是 1 人 × 2-3 个月业余时间 + 每月 1-2 天的数据维护。
  6. 合规要点三个：榜单引用标注来源、底座只用 MIT/Apache-2.0、页面挂免责声明——即可放心推进。
  7. 把"留存机制"从第一天就设计进去：用户价值分析显示"选模型"是低频行为，P1 必须包含模型换代提醒（榜单发现更优模型时推送"你的策略该更新了"）与用量成本看板，否则产品会沦为"用完即走"的一次性工具。

八、决策视角：如果由我拍板，方案怎么调

前面七章是"这个方案可不可行"的客观评估；本章是"如果我是出钱出时间的那个人"的主观决策——有几处反直觉的调整，供你参考取舍。

8.1 我的核心判断：当前方案最大的风险不是技术，是"单人副业的时间预算"

方案评估显示 80% 的长期成本在排名站的数据维护——这意味着按原方案，你要为一个"没有差异化"的组件付出最多的持续成本。同时，全职工作之下每天可投入时间有限（约 1 小时），2-3 个月的估算是偏乐观的。单人副业项目的头号死因不是做错，是范围蔓延 + 维护负担 → 烂尾。所以我的所有调整都围绕一条原则：用最小的维护成本，最先验证最大的不确定性。

8.2 四处关键调整

调整原方案我的决策理由
① 排名站降级：产品 → 副产品 P0 花 3-5 周做精雕细琢的排名网站 只接 2-3 个 API（OpenRouter + Artificial Analysis），做自动生成的模型详情页/对比页，不做看板级打磨 正面刚 DataLearner/AA 没有胜算。排名站对你只有两个不可替代作用：给策略引擎供数据 + SEO 长尾引流。做到这两个目的的最低限度即可，省下的时间全投差异化层
② 顺序反转：核心假设先验证 P0 排名站 → P1 策略生成器 先做 2 周的开源小工具验证：输入模型清单+任务+偏好 → 输出 LiteLLM 配置文件，挂 GitHub / V2EX / 掘金，用 Star 和反馈说话 最大的不确定性不是"排名站有没有人看"（已被验证有），而是"策略生成器有没有人用"。原方案把前 3-5 周花在不验证核心假设的事情上，顺序反了。V0 失败成本只有 2 周，可以承受

8.4 决策依据与保留意见

  • 唯一稀缺资源是你的持续投入时间，不是钱、不是技术。所有调整都在削减"维护型工作"，保留"资产型工作"（策略映射规则、开源项目口碑是可累积的；榜单数据维护是纯消耗）。
  • 保留意见（诚实说明）：我这个调整牺牲了排名站的"产品竞争力"——如果未来 V2 发现流量主要来自搜索而非开源社区，需要回头补做排名站打磨。这是一个有意识的赌注：赌开发者社区的传播效率高于 SEO。
  • 如果只能做一件事：做策略生成器。它是整个方案里唯一"没人做过 + 你能做好 + 验证最便宜"的交集。
