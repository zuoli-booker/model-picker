# 05 - 开源借鉴与架构说明（不重复造轮子专项）

> 版本 v1.0｜PM：WorkBuddy/阿腾｜2026-09-28
> 起因：左力要求项目核心理念为"在成熟开源方案基础上做，不重复造轮子"。本文档是这一原则的系统化落地：核查了什么、借了什么、为什么不借什么。
> 本文档独立于 docs/04（Trae 的开发依据），不改动已交付的 PRD。

## 1. 核查结论：模型选型推荐类开源项目

2026-09-28 开发启动前专项核查 GitHub 上的相近项目：

| 项目 | 方向 | 与本项目的重叠度 |
|---|---|---|
| **richard-gyiko/which-llm** | CLI + Agent Skill，基于 benchmark + 成本推荐模型（数据源自 Artificial Analysis，每日更新） | **高**——概念最接近 |
| Andyyyy64/whichllm | 硬件感知的**本地模型**选择（Ollama 本地部署） | 低——不重叠 |
| AlexsJones/llmfit（MIT） | 硬件感知的本地部署选型（Rust TUI） | 低——不重叠 |
| Pavelevich/llm-checker（2.6k★） | Ollama 本地模型选型 | 低——不重叠 |
| LLMSELECTOR | 学术框架：compound AI 系统内各模块模型分配自动优化 | 低——面向研究者 |

**关键发现**："本地模型选型"已有多名玩家；"云端 API 模型选型推荐"目前仅 which-llm 一个雏形（英文、全量推荐、无配置产出）。**我们的定位（BYOK 清单内推荐 + 配置产出 + 中文非程序员）依然空白。**

## 2. 为什么 which-llm 可借鉴但不 fork

| 对比项 | which-llm | 若 fork 改造成本 |
|---|---|---|
| 语言/技术栈 | Rust，需 cargo 构建 | 中文用户需装 Rust 工具链？不可接受——违背"非程序员 10 分钟上手"验收标准 |
| 推荐逻辑核心 | 全量模型推荐 | 本项目核心约束是**用户手头模型清单**——输入层完全不同，核心逻辑需重写 |
| 产出物 | 推荐列表（只到"建议"） | 本项目要到"配好"（LiteLLM yaml）——输出层需新增 |
| 数据 | 预编译 SQLite 快照（许可证未确认） | 不能直接用，还是得走 AA 官方 API |
| 许可证 | 未确认 | 引入不明许可证风险违背"只用 MIT/Apache-2.0"硬约束 |

**结论：fork which-llm ≈ 重写**。它的价值不在代码，在**验证过的做法**（见第 3 节）。

## 4. 需要重新开发吗？——不需要

**当前 MVP（Trae 开发中）不需要重做**，理由三条：

1. **通用轮子已经全部借到位**：路由/配置用 LiteLLM、数据用三家官方榜单、运行时用 Python 标准库零依赖。自己写的只有"清单约束评分 + 配置生成 + 中文问答"这一薄层——**这正是产品的价值所在，也是差异化壁垒，这部分本来就不该用别人的轮子**。
2. **可借的整项目（which-llm）与我们的形态差异太大**：fork 它意味着推翻"非程序员中文用户、零依赖、BYOK 清单约束、配置产出"四个已拍板决策，且其数据许可证未确认。借它的"做法"（数据路线、skill 标准、任务分类）零成本，借它的代码反而引入风险。
3. **开发已经完成大半**：Trae 的 F2 推荐引擎、F4 三产物、README 均已提交，重新开发 = 沉没成本翻倍，违背"最小成本验证最大不确定性"原则。

**但有一个前置校验必须在门1 前做**：核查 which-llm 等同类项目的许可证与数据使用条款，确保我们的推荐逻辑、数据引用方式（榜单标注来源）没有法律风险。这是 PM 待办，不阻塞开发。

## 5. 决策记录（2026-09-28 左力已确认 ✅）

| 决策 | 建议结论 |
|---|---|
| 是否 fork which-llm | **不 fork**，借鉴其做法不借鉴代码 |
| 当前 MVP 是否重做 | **不重做**，维持 Trae 开发版本 |
| "不重复造轮子"原则的落地口径 | **通用部分全借成熟组件，差异化薄层自研**；每次引入新功能前先核查 GitHub 是否已有成熟方案 |
