| 事实 | 复核结果 |
|---|---|

**两个新情报**（本次复核新发现，对设计有影响）：

1. **APUS 已交出全球首批跨平台开源复现 Jev**（2026-09-20 报道）——"Jev 协议"正在成为事实标准，开源实现不止 Laya 一家；
2. 品类出现 **kev 等更多 System One 玩家**——决策模型品类在快速分化。

→ 设计含义：**我们的抽象层应该锚定"Jev 线协议"而不是锚定某家引擎**。谁兼容协议谁就能插进来，换引擎零代码改动。这直接把"双引擎"的实现成本从"两套集成"降为"一套客户端 + 两个 baseUrl"（见 4.1）。

## 4. 关键设计

### 4.1 决策引擎协议抽象：一套客户端，两个（乃至 N 个）引擎

核心洞察来自第 2 节：**laya-serve 的接口完全兼容 Jev 线协议**（客户端只需换 baseUrl）。因此"双引擎"在代码层面不是两套集成，而是：

```python
# 决策引擎配置（路由应用 config.yaml 片段）
decision:
  engine: jev          # jev | laya | rule（默认 rule）
  threshold: 0.6       # 置信度阈值
  timeout_ms: 800      # 决策超时
  jev:
    base_url: https://api.typesafe.ai   # 用户 BYOK
    api_key: os.environ/TYPESAFE_API_KEY
  laya:
    base_url: http://laya-sidecar:8080  # 本地 sidecar，零费用
```

- JevEngine 与 LayaEngine 共用同一个 Jev 协议客户端，差别只有 baseUrl + 是否带 Key；
- 未来 APUS 复现版、kev 或任何 Jev 协议兼容实现（含 1Panel 的 Laya Server），都是"再加一个 baseUrl"，不改代码；
- `engine: rule` 是内置兜底：不调任何外部服务，按启发式规则（关键词/长度特征）映射任务别名，映射不了就走默认别名。**规则式永远在场，引擎只是增强**——这是 5.5 节"规则式永远兜底"的落地方式。

### 4.2 routing-goals.yaml：schema 与生成规则

```yaml
# 由 model-picker 生成 —— 智能路由目标定义（Jev/Laya 通用）
version: 1
goals:
  - id: writing
    name: 写文案/周报
    include: 写作、改写、润色、周报月报、总结汇报、通知公告等中文成文任务
    exclude: 需要执行/生成代码的任务；超长文档的阅读理解
    examples:
      - "帮我把我这周做的事件整理成一段周报"
      - "把这段话改得更正式一些"
    route_to: writing          # 命中后使用的 LiteLLM 别名（即 model-picker 已生成的别名）
  - id: coding
    name: 写代码/改代码
    include: 编写、修改、调试、解释代码，技术方案实现
    exclude: 只聊编程概念不产出代码的讨论
    examples:
      - "写一个 Python 脚本批量重命名文件"
    route_to: coding
  # ……其余 4 个任务类型
```

生成规则：

- **字段名（name/include/exclude/examples）对齐 1Panel Jev 模式的目标字段**——它是目前最完整的生产实现，照抄字段结构可少走弯路；
- `include`/`exclude`/`examples` 的初版文案由 model-picker 内置维护（PM 侧资产，与权重表同等地位），从 TASKS 的任务语义+维度权重推导；
- 1Panel 经验（官方发布文章）：**目标间语义边界要清晰、排除说明要写"容易混淆但不该进来的情况"**——6 任务类型天然互斥性较好（写作/翻译/长文档/代码/数据/日常问答），处于 Jev/Laya 的舒适区（选项 ≤20）；
- 留 `route_to` 而不直接用 id 做别名，是为了允许用户自定义别名后仍能对上。

### 4.3 auto 入口与请求流水线（含数据边界）

请求处理顺序：

```
收到请求
  ├─ model ≠ auto → 直接透传给 LiteLLM（零开销，兼容存量用法）
  └─ model = auto
      ├─ 熔断开启中 → 跳过决策，直接走兜底别名
      ├─ 决策引擎 = rule → 规则式判断任务别名（不发出任何外部请求）
      └─ 决策引擎 = jev/laya
          ① 提取数据：仅「截断后的当前用户文本」+ 2 个特征
             （has_tools: 是否含工具声明；truncated: 是否被截断）
             ——系统消息、历史对话、凭据、模型清单一律不发（照抄 1Panel 数据边界）
          ② 调 Jev 线协议 Choice：goals 数组 → 返回目标 + 概率 + 置信度
          ③ 超时（默认 800ms）或异常 → 计入熔断计数，走兜底别名
      → 按 route_to 改写 model 为任务别名 → 转发给 LiteLLM（流式原样透传）
```

设计要点：

- **截断长度**：默认 1000 字符（可配）。1Panel 未公开具体数值，我们按"足够分类、最小暴露"自定，中文 1000 字符足以判别任务类型；
- **流式响应**：决策只发生在转发前的一次调用，响应字节流由代理原样透传、不解析——避免流式转发引入 bug 的最简做法；
- **成本**：Jev 输入 $0.042/MTok，1000 字符 ≈ 千 token 量级 ≈ **每次决策约 $0.00005**，相对一次 LLM 调用（¥0.001~0.05）占比 <1%；Laya 本地免费。熔断期间成本为零；
- **延迟**：决策增加 30~500ms（Laya CPU 200-460ms / Jev 含网络 236-523ms），一次性开销，叠加在 LLM 首 token 延迟（通常 500ms~2s）之上可接受；对延迟极敏感的用户可设 `engine: rule`。

### 4.4 置信度路由与兜底熔断状态机

```
                    ┌────────────────────────────────┐
                    │  Jev/Laya 返回 {goal, prob, conf} │
                    └───────┬────────────────────────┘
              conf ≥ τ(0.6) │        conf < τ 或 other
                    ▼                                ▼
          进 goal.route_to 别名              进兜底别名（fdefault）
                                              = 用户问答第3步偏好对应的
                                                规则式首选任务别名
      引擎侧异常/超时 → 失败计数 +1；连续 3 次 → 熔断 60s
      熔断期间所有 auto 请求直走兜底；60s 后半开试探 1 次，成功则恢复
```

- **τ 初始 0.6、可配**，后续用真实决策日志校准（日志里有"决策结果 vs 用户实际满意度"的可观测代理——见 4.5）；
- **兜底别名必须是 model-picker 策略里已存在的别名**（不新造模型组），保证"决策引擎挂了 = 退回规则式"这一等价关系成立；
- 熔断三参数（阈值 3 / 冷却 60s / 半开 1 次）写死为常量即可，不做配置项——非程序员用户不需要理解熔断。

### 4.5 决策日志（可解释性的落地）

本地 JSONL，追加写，默认永不离开用户机器：

```json
{"ts":"2026-10-20T14:32:11+08:00","request_id":"a1b2","text_sha256":"…","text_len":842,
 "text_preview":"帮我把这周的…（前64字符，可关闭）","engine":"jev","goal":"writing",
 "probabilities":{"writing":0.71,"translation":0.15,"chat":0.08},"confidence":0.71,
 "latency_ms":312,"decision":"route","fallback_reason":null,"engine_tokens":1090}
```

- 字段对齐 1Panel 决策日志（目标/概率/置信度/Token/时延/回退原因）+ 我们补 `text_sha256`/`text_preview`（脱敏排障用，preview 可关闭）；
- **双重用途**：① 用户侧可解释（Web 控制台展示"这条请求为什么走了写作模型"）；② 项目侧数据资产（阶段3 校准 τ、优化 goals 文案、微调 Laya 的评估集）；
- 隐私红线：日志功能不绑定任何上传通道。未来若做"可选上传换服务"，属于方向性决策，须左力另行拍板。

### 4.6 决策代理形态选型：前置薄代理 vs LiteLLM 进程内 hook

| | 前置薄代理（推荐） | LiteLLM pre-call hook |
|---|---|---|
| 原理 | FastAPI/httpx 小服务，拦 auto 改写后转发给 LiteLLM | 把决策代码作为 Python 插件注入 LiteLLM 进程 |
| 故障隔离 | 决策引擎挂掉不影响 LiteLLM；代理本身挂掉=整个应用不可用（需 keepalive 重启） | hook 异常可能影响 LiteLLM 主流程 |
| 与 model-picker 衔接 | LiteLLM 配置零感知，直接加载现有产物 | 需要把插件打进 LiteLLM 镜像 |
| 引擎独立升级 | sidecar 独立容器，随便换 | 耦合在网关进程 |
| 多一个服务/端口 | 是（compose 内网，用户无感） | 否 |

**推荐前置薄代理**：多一个容器对 Docker Compose 用户零感知，换来故障隔离和"LiteLLM 保持原味"（升级 LiteLLM 不用回归测试插件）。备选方案 hook 记录在案，若未来发现代理透传流式有性能问题再切换（两者对外行为一致，切换不涉及用户）。

## 5. 可行性论证

### 5.1 技术可行性：成立

- 所有依赖满足协议白名单：LiteLLM（MIT）、Laya 模型+laya-serve（Apache-2.0）、FastAPI/httpx（MIT）；Jev 是商用 API 服务（用户 BYOK，无协议问题）；
- Jev 线协议已成为事实标准（Laya 官方兼容 + APUS 复现 + 1Panel 采用），客户端实现风险低；
- 1Panel v1.3 已在生产环境跑通同构架构（auto 入口 → 决策 → 调度 → 兜底熔断），我们等于站在已验证的参照系上做差异化；
- 6 任务分类场景落在决策模型舒适区（选项 ≤20，语义边界清晰）。

### 5.2 经济可行性：成立

- 决策成本每次 <$0.0001（Jev）或零（Laya/rule），相对被路由的 LLM 调用成本占比 <1%；
- 自研代码量 <600 行，无持续云成本（路由应用本来就是用户自托管）。

### 5.3 维护成本核算（决策闸：≤2h/月）

| 维护项 | 频率 | 预估耗时/月 |
|---|---|---|
| 决策代理代码（<500 行，依赖稳定） | 按需修 bug | ~0.5h |
| Jev/Laya 协议跟踪（线协议稳定为事实标准，主要盯公告） | 月度扫一眼 | ~0.2h |
| routing-goals 文案调优（由决策日志驱动） | 月度，阶段3 起 | ~0.5h |
| Laya 模型/laya-serve 版本升级 | 季度 | ~0.3h（摊月） |
| **合计** | | **≈1.5h/月 ✅ 过闸** |

⚠️ **一个明确的超闸项：Laya 微调管道**（标注集维护+训练+评测）。若我们自维护微调管道，月维护将远超 2h。对策（阶段3 时再定）：**优先采用 Laya 官方/社区发布的微调版权重，我们不养管道**；仅当社区权重在 6 任务分类上实测不达标且用户日志价值足够大时，才提请左力重议（届时按"实验性插件"定位，不进主干）。

### 5.4 风险与对策表

| # | 风险 | 概率/影响 | 对策 |
|---|---|---|---|
| 1 | Jev 托管服务变动（涨价/停服/协议改） | 中/低 | 熔断兜底保证可用性；协议抽象保证可切 laya 或任何兼容实现；文档明示"决策服务是增强非依赖" |
| 2 | Laya 微调后 6 任务分类仍不达标 | 中/中 | 集成闸：实测准确率 ≥85% 才开 laya 选项（AGENTS.md 决策闸原文）；不达标就只留 jev，架构不受损 |
| 3 | 品类快速演化（kev/APUS/新玩家），押错引擎 | 中/低 | 我们押的是**协议**不是引擎——谁赢都兼容我们；这正是 4.1 设计的动机 |
| 4 | 1Panel 等成熟团队把智能路由做成免费标配 | 高/低 | 巨头卷"网关"，我们做"选型决策层 + 非程序员体验 + model-picker 数据闭环"（docs/06 §三.8 判断维持，且 1Panel 是服务器面板、面向运维，与轻开发者人群错位） |
| 5 | 决策代理的流式转发 bug | 低/中 | 字节流原样透传不解析；代理挂掉时 compose 自动重启；用户可绕过 auto 直用别名逃生 |
| 6 | 用户误配（Key 填错、sidecar 未启动） | 中/低 | 启动时"测试决策引擎"自检（对齐 1Panel 的测试连接）；失败则自动回落 rule 并在控制台提示 |

### 5.5 论证总结

**结论：可行，且是"低成本增强"而非"新造系统"。** 成立的前提是三条纪律，全部已内建于设计：① 规则式永远在场（引擎只是可插拔增强）；② 分阶段（阶段2 只做骨架，阶段3 才接引擎）；③ 两道闸约束（Laya 准确率 ≥85% 才集成、维护 ≤2h/月，微调管道不进主干）。

## 6. 分阶段落地路径

### 阶段2（路由应用 MVP 交付时）——只做"骨架"，不含任何决策引擎

| 交付项 | 工作量 | 说明 |
|---|---|---|
| auto 别名占位 | 极小（一条配置） | auto = 兜底别名（用户偏好对应的首选任务）。**先把 auto 语义占住**，智能体侧从此不用改，阶段3 开引擎时用户应用零改动 |
| 决策代理容器骨架 | ~300 行 | 透传 + auto 拦截 + 决策日志落盘，engine 固定为 rule |
| routing-goals.yaml 生成器 | ~50-80 行 | model-picker `--goals` 参数，第 4 产物。schema 先固化，阶段3 直接消费 |
| 决策日志 schema | 随代理落地 | 从第一天开始积累校准数据 |

阶段2 验收：auto 请求全链路可通（决策日志有记录）、关掉代理容器后直连 LiteLLM 别名仍可用（逃生通道验证）。

### 阶段3（产品化闭环后）——"智能决策模式"

| 交付项 | 前置闸 |
|---|---|
| jev 模式（用户填 TypeSafe Key） | 无前置闸，协议客户端就绪即可开 |
| laya 模式（sidecar 一键开启） | **集成闸：Laya 在 6 任务分类实测准确率 ≥85%**（用阶段2/3 积累的决策日志做评估集；优先测社区/官方微调版权重，不自养微调管道） |

| Web 控制台展示决策理由 | 可解释性 UI，随控制台排期 |

## 8. 对 docs/06 §6 三项待确认决策的建议（供左力拍板，本文不拍板）

### 建议①：双引擎目标架构——**建议确认，附两点细化**

- 确认"Jev（BYOK）+ Laya（本地）双引擎可切换、规则式永远兜底"的目标架构；
- 细化一：建议在写入 docs/02 时表述为"**锚定 Jev 线协议的决策引擎抽象**，Jev/Laya（及任何协议兼容实现）均为可插拔端点"——比"双引擎集成"更准确也更抗品类演化（第 2 节新情报：APUS 复现、kev 出现）；
- 细化二：建议明确启用顺序——**jev 模式随阶段3 开放（无前置闸），laya 模式需过准确率 ≥85% 集成闸**（原因：Laya 零样本不可用是作者自认的硬短板，而 Jev 是托管成品）；
- 理由汇总：1Panel v1.3 已生产验证同构架构；我们差异化在选型决策层而非网关，与其无正面冲突。

### 建议②：MVP 增加选择日志——**建议授权，给 Trae 的任务卡已在下面拟好**

- 工作量：约 0.5-1 小时，零新依赖，不改变任何现有交互；
- 任务卡（可直接派给 Trae）：
  - 改动点：`quiz.py` 第 4 步用户确认生成时，追加一行到 `~/.model-picker/choices.jsonl`（目录不存在则创建；该路径加入 .gitignore）；
  - 记录字段：`{"ts": ISO时间, "task_ids": [...], "priority": "balanced", "model_count": N, "preset": 预设名或null, "app_version": __version__}`——**不记模型名与任何可识别信息**；
  - 明确不做：无上传功能、无统计上报、README 加一行说明（"本地记录，可随时删除该文件"）；
